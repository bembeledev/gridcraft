# Large workbook performance

> **Last reviewed:** 2026-10-26 · **Last updated:** 2026-10-26 · **Change:** minor (re-measured after merging main; graph reuse for tables and every visibility-only edit; `cargo xtask bench`)

## Method

The native-only `crates/ui-egui/examples/large_workbooks.rs` benchmark generates deterministic
workbooks in memory. Production has no per-cell timing or allocator interception. Optional
`GRIDCRAFT_PROFILE=1` extends the existing commit/calc logging with filter preparation,
predicate evaluation and visibility-update timings. Keep it off for comparisons.

Run it on any platform with:

```sh
cargo xtask bench --label current --repeats 5
```

`cargo xtask bench` builds the example in release, then runs the datasets one process at a
time (`--datasets A,B` picks some) and records in `target/perf/<label>/` each dataset's
stdout (with the example's p50/p95/p99) and stderr, the source commit and working-tree
status, `rustc -Vv`, the hardware, the SHA-256 of the executable (and of an input
workbook) and each process's peak memory: the peak working set on Windows, `VmHWM` on Linux
and the largest `ps` resident-size sample elsewhere (every 100 ms). To compare two source
checkouts, build each in **its own Cargo target directory** and pass the other build with
`--exe <path>` (its `commit.txt` then names the runner's checkout, not the executable's);
run both on the same machine with no concurrent builds or benchmarks. A and H share values;
both run 89% and 9% selectivity numeric filters. Repetitions are warmed within one process
and include the first operation (cold caches); each dataset starts a new process.

| Dataset | Rows by default | Contents |
|---|---:|---|
| A | 100,000 | 12 numeric columns, no formulas |
| B | 100,000 | 9 numeric columns + 3 formulas per row (300,000 formulas) |
| C | 100,000 | Text, numbers, date formats; explicit variable height on every data row |
| D | 500,000 | 2 numeric columns |
| E | 1,000,000 | 2 numeric columns |
| F | 100,000 | 2 columns, stored only every 1,000 rows |
| G | 100,000 | Numeric input + cumulative formula dependency chain |
| H | 100,000 | A with both filter selectivities |

Row counts exclude one header. Synthetic workbooks are generated by GridCraft, never
Microsoft assets, and are the reproducible evidence for this work.

The separate `workbook_file_perf` example measures file read/import, initial
graph/calculation, complete open, numeric filters on the largest sheet, CPU frames and
saving to memory for any workbook: `cargo xtask bench --label <name> --input <book.xlsx>`.
The real workbook quoted below is **private** to the contributor (7,627,635 bytes,
SHA-256 `18be34eeeb595391759bc9dd411af0aef0640fadbd43d4f96d5de6cea7854776`, 100,000 data
rows, 300,012 formulas). It is not in a corpus repository, so others cannot reproduce those
rows; the hash only identifies the input. It is opened read-only and never written or
committed. Adding a comparable public workbook to the pinned, sha256-verified test corpus
(craftrules `standards/test-corpora.md`) is follow-up work.

`scroll_cpu_frame` times `egui::Context::run_ui` including UI logic/layout/paint preparation
while moving through the sheet, at 1440×900 logical points, after five warmup frames.
It excludes tessellation, GPU submission, vsync and presentation. It is **not actual FPS**.
There are 100 frame samples and 50 geometry/range samples with five repetitions. Filter,
save, read and recalc have five samples; p95/p99 with that sample size are just maxima.
The quantile method is nearest rank. `full_recalc` includes dependency-graph construction.
Do not add percentiles to claim a measured end-to-end open time. Peak memory covers the whole
dataset lifecycle, including retained allocator capacity and repeated XLSX operations.

## Diagnosis

Measured on the original baseline `d9d09f0` (2026-10-14):

| Path | Cause | Baseline evidence |
|---|---|---|
| `model/store.rs::used_range`; both `ui-egui/grid.rs` scrollbars | Repeated full scan of stored rows to find column extrema, despite virtualized painting | A: two queries p50 13.307 ms; E: 48.445 ms |
| `ui-egui/grid.rs::Geo::new` | Rebuilds dimension prefix sums and outline groups whenever geometry is made | C: construction p50 1.512 ms, p95 3.245 ms |
| `engine/cmd/data.rs::apply_filter` | Formats values even for numeric/statistical/color criteria; clones values; parses numeric criteria per row | A: filter p50 164.294/179.696 ms |
| `engine/cmd/mod.rs::commit` → `calc/recalc.rs::recalc_all` | Visibility change rebuilds dependencies and evaluates every formula | B: 300,000 evaluations per filter; filter p50 1,247.114/1,196.645 ms; full recalc 1,040.218 ms |
| `engine/cf.rs::CfCache::look`; `ui-egui/grid.rs::show` | Every visible cell cloned complete range statistics; even cell-local rules populated those statistics | Real workbook: one `cellIs` rule on K2:K100001; CPU frame p95 453.604 ms before optimization |
| `xlsx/read.rs`, `package.rs`, `sheet_read.rs` | Whole-workbook import, not streaming; shared strings already use `Arc<str>` and styles are interned | B: read without calc p50 3,811.230 ms; no import optimization proven yet |

The conditional-format cost was fixed independently on main (#1098: statistics only for the
rules that read them, borrowed rather than cloned per cell), which this branch now uses.
Cell storage already uses sparse row-major BTreeMaps in 64-row copy-on-write bands.
Calculation already has incremental dirty propagation, indexed range dependencies,
bounded evaluation, and shared formula expressions. The grid already paints viewport panes;
the diagnosed costs are outside that virtualization. No storage replacement, thread pool,
parallel recalc or permanent filter index is introduced.

## Navigation changes and invalidation

`CellStore` caches one optional rectangle in `OnceLock`, populated on first query. A new
cell extends a warm cache (`RangeRef::union`); removing a cell drops it only when the cell
lies on an edge of the rectangle, because every edge holds a stored cell and an interior
removal cannot shrink it. Changing an existing cell's content/style keeps it valid. Range
removal and shifts use those same mutators; `get_mut` cannot change stored coordinates.
Cloning preserves an independent cache; serialization omits it and equality ignores it. A
seeded test runs every mutator on a warm cache and compares the result with a fresh scan.

`GeometryCache` retains one sheet's row/column indexes and outline axes. Its key is what they
are built from: the explicit row and column metadata, the default row height and column
width, and the outline's summary side. A `Weak<Sheet>` of the last snapshot skips comparing
the key while the sheet is unchanged (it retains no cell data, and a held `Weak` keeps its
address from being reused); `Arc::make_mut` detaches weak pointers even with one owner, so
any edit compares the key. Zoom, cell, view and selection edits therefore reuse the indexes;
filters, resizing, outline edits, defaults, switching sheets/documents and undo snapshots
that change the lines rebuild them. Zoom, scroll, freeze placement, RTL and viewport
geometry are read afresh. The cache holds one copy of one sheet's explicit line metadata.

## Filter and conditional-format changes

Each filter criterion is prepared once per filter (value set, parsed numeric operands,
top/bottom threshold, average, colours); numeric, color and statistical predicates do not
format text unnecessarily. Value lists use a temporary ASCII-folded hash set, preserving
`eq_ignore_ascii_case` semantics (not Unicode case folding). Both raw and formatted display
values still match, and blanks remain separate. No permanent per-column index is kept.

Visibility-only edits — filters (apply, reapply, clear), turning a sheet AutoFilter off,
hiding/unhiding rows and columns, Hide/Show Detail and the outline level buttons — re-evaluate
every formula with the existing dependency graph. This does not skip volatile formulas,
visibility-sensitive functions, dynamic spills or cycles. Before reusing the graph, `commit`
checks that the sheets, calculation settings, defined names, tables and formulas are
unchanged (comparing only the cell bands the edit touched) and otherwise recalculates in
full. Any changed cell uses the original rebuild. Table header synchronization clears the
flag only when it rewrites a header cell or renames a column (which rewrites structured
references); filtering a table that keeps its headers reuses the graph. `Calc::graph_rebuilds`
lets tests observe which path ran.

Conditional-format statistics keep counting the rows a filter hides, as Excel does: with
`A2:A11 = 1..10` filtered to `A>5`, "above average" still compares with 5.5 and "bottom 2"
still marks the hidden 1 and 2 (`statistics_of_a_filtered_range_still_count_its_hidden_cells`).

## Measurements on the merged tree (2026-10-26)

Machine: Intel Core i7-1165G7, 4 cores / 8 logical processors, approximately 16 GiB RAM,
Windows 11 Pro 10.0.26300; rustc 1.99.0 (`b940084d7`, x86_64-pc-windows-msvc). Release:
opt-level 3, thin LTO, 16 codegen units, debug 0; no profiling variable; no concurrent
builds. Candidate: this branch at commit `07e241a6` (clean working tree). Baseline: upstream
main `d8c5f588`, built from a separate worktree and target directory with the same two
example files (its `large_workbooks` omits `geometry_cached`, as main has no
`GeometryCache`). Background system activity, power state and thermals were not
instrumented. Raw runs: `target/perf/synth-main`, `synth-pr`, `real-main-1..5`,
`real-pr-1..6` (gitignored). Executables (SHA-256 prefixes): candidate `c1ba7c9e` /
`b49cc424`, baseline `09c7c230` / `f84a2085` (synthetic / real-file).

with more than about one million XML elements as damaged and keeps only the rows read so far

its 100,000 data rows** (399,984 cells, 100,005 formulas, one import warning). The real-file
numbers below compare main and this branch on that same partial load; they are not
comparable with the full-workbook numbers of 2026-10-14. The synthetic datasets are built in

real-file frame gain is now in main itself. The <4 s open target is met only because two
thirds of the rows are not loaded; the <500 ms filter target is not met reliably. GPU FPS is
not measured.

## Earlier measurements (2026-10-14, before merging main)

The first version of this branch (`d54be6f`, uncommitted at measurement time) was compared
with `d9d09f0` on the full real workbook (100,000 data rows, 300,012 formulas evaluated per
filter): CPU-frame p95 518–524 → 6.21–6.25 ms, filters 1.86–2.40 → 1.28–1.43 s, complete open
4.81–5.40 s with no stable difference, peak working set about 2.8 GB on both. Synthetic
CPU-frame p95 fell 51–84% and filters 6–90%. Those numbers predate main's own changes (#1098
and later) and are kept only as history; the merged-tree tables above supersede them.

## Checks

`cargo xtask ci` on this machine at `07e241a6`, with `CRAFT_FONTS_DIR` set to craft-fonts
`b076417` as upstream CI pins it: i18n-report, fmt, clippy (`-D warnings`), workspace tests
(**2,542 passed, 0 failed, 1 ignored**: the timing-sensitive
`recalc_with_range_formulas_scales_linearly`), doctests, assets, layers and WASM passed.
`parity --check` and `keytips --check` reported their generated files out of date only
because the Windows checkout (`core.autocrlf=true`) has CRLF line endings; regenerating them
produced no content change and both checks then passed. Without craft-fonts, two UI tests
(`column_autocomplete_folds_case_beyond_ascii`, `language_switch_renders_the_ribbon_and_persists`)
fail on missing glyphs, as they do on main.

Two fixes to main code were needed for these gates to run on Windows: a symlink test without
`#[cfg(unix)]` (engine `io.rs`) and clippy's `only_used_in_recursion` on the unix-only
identity set in `gridcraft-cli check`. Neither changes behaviour.

GPU FPS, separate text-layout timings, allocation counts and post-close process RSS are not
measured. G exercises a long chain, not a representative multi-sheet production graph.
Geometry construction, filter preparation/predicates/visibility (opt-in profiling), full UI
CPU frames and total read/import are measured at their respective boundaries, not inferred
as finer phases.

## Known differences from Excel

- In manual calculation mode a filter (or any other structural commit) still recalculates
  every formula immediately; Excel leaves `SUBTOTAL` and its dependents stale until F9.
  Cell edits already respect manual mode. Selective recalculation on visibility changes is
  follow-up work (#208, #2122), as is honouring manual mode there.
- Value-list filters fold case for ASCII only, and a number filter value also matches the
  raw number of a date-formatted cell; both come from main's predicates and are preserved.
